# 初始化项目

## 前置检查

初始化只收集信息和建立 Harness，不负责安装或升级 Agent、模型或认证环境。先确认：

- 当前 Agent 能加载 `perpetuum` 与必须依赖的 `cc-use` Skill；
- `uv` 与 `tmux` 可用；
- 对应的交互式 Codex 或 Claude Code TUI 可启动；
- MemSearch 是可选依赖；可用时检索历史，不可用时直接跳过。

不要在初始化过程中更新 Codex、Claude Code、模型或认证配置。版本不兼容时说明现状和影响，让用户决定是否另行处理。

## 共同设计原则

初始化不是根据一句目标自动补齐配置，而是与用户共同设计一套将长期运行的 Harness。先区分三类内容：

- **实现硬边界**：Runner、Project Supervisor、Story Supervisor、cc-use session 所有权等 Perpetuum 固定机制。向用户解释其影响，不伪装成可选项。
- **用户已经明确的决定**：直接纳入契约，不重复询问；如果彼此矛盾或与硬边界冲突，再指出具体冲突并请用户选择。
- **尚未明确的决定**：凡是会改变工作内容、角色、顺序、权限、产物、验收、运行时间、成本、外部影响或人类介入方式，都必须询问用户，不得用默认值、惯例、历史偏好或 Agent 的合理推断静默补齐。

“Agent 建议这样做”不等于用户已经同意，用户没有反对也不算确认。用户明确说“你决定”“按你的建议”或等价表达时，才算把该项选择权委托给 Agent；Agent 应记录选择及理由，并仍把结果放入最终完整契约让用户确认。

## 自适应询问流程

1. 解析候选项目目录并只读检查项目文件和可用历史。若 MemSearch 可用，用它召回历史，再以项目证据复核；此时不创建 Harness。
2. 先向用户说明 Perpetuum 的固定架构，再列出“已明确”和“待决定”的高层事项。从最影响后续设计的问题开始询问，不从 cron 或字段细节开始。
3. 每轮集中询问一组紧密相关的问题，通常一至三个；每个问题都指向一个具体决定，说明为什么需要决定，并给出基于当前项目的建议、备选项和主要权衡。不要把架构设计责任全部丢给用户，不要用“还有别的吗”代替逐项确认，也不要一次发送一张庞大问卷。
4. 根据回答更新当前契约和待决清单。一个回答引出新的依赖问题时继续追问；已经明确的事项不重复询问。简单 Harness 可能一两轮完成，复杂 Harness 可以经过多轮。
5. 架构明确后再起草第一批 Story 和运行计划。发现 Story 暴露出新的角色、权限、验收或循环问题时，回到对应事项继续询问。
6. 待决清单清零后，展示一份合并后的完整契约，清楚区分用户原始决定与经用户授权后由 Agent 选择的内容，并明确请求用户确认是否按此建立 Harness。
7. 只有用户确认当前这份完整契约后才能注册项目。用户修改任何内容后，先更新合并版并再次确认；不能把对其中一个问题的回答当作对整个 Harness 的授权。

用户想把某项留到以后决定时，继续询问“在决定前采用什么安全行为”。把用户确认的默认暂停、禁用或不执行策略写入契约，不能保留一个会让运行中 Agent 自行猜测的空白；实际 `paused`、`enabled`、时区和 cron 当前值只写入 `schedule.yaml`，不要在 Goal、History 或 `team.md` 复制成会过期的当前事实。

## 必须明确的设计面

按依赖关系逐步询问，而不是机械照表提问。用户没有明确说明时，至少要覆盖：

- **目标与项目边界**：项目目录和名称、长期 Goal、当前背景与进度、成功证据、明确不做什么。
- **工作模型**：每次激活推进一次性 Story 还是重复例行任务；工作单元如何划分；每轮输入、产物、完成记录、失败处理，以及下一轮如何恢复为可运行状态。
- **队伍架构**：Executor 的职责、输入、产物、权限和边界；Validator 与 Explorer 是总是启用、从不启用还是按什么明确条件启用；各角色的触发点、调用顺序、反馈回路、终止条件和 session 复用关系；每个直属 session 的精确名称与 `finish` 结果如何持久化；未启用 Validator 时由谁按什么证据接受结果。
- **运行与恢复**：Agent 类型、项目时区、一个或多个标准五字段 cron；在“同项目不重叠激活”这一硬边界下如何处理错过的轮次或积压；外部等待、重试边界、暂停与恢复方式。
- **资源与授权**：允许使用的数据、工具、账号、服务和机器；可以执行哪些外部写入、发布、通知、付费或破坏性动作；成本、安全、隐私和合规底线。没有明确授权的外部副作用不得写成默认能力。
- **人类参与**：什么情况必须提 Question，什么情况属于 Escalation；人类需要看到的报告内容、频率和决策入口；长期目标之外必须兼顾的要求。
- **初始看板**：第一批 Story 的标题、摘要、优先级、标签、背景、范围、边界和验收标准；若初始应当 Idle，也必须由用户明确确认。

角色建议应与风险相称：机械、低风险、产物容易直接检查的例行任务可以建议只用 Executor；目标开放或需要持续发现后续工作时建议增加 Explorer；结果影响用户、产品或外部系统，或失败代价较高时建议增加独立 Validator。每一项都要让用户明确选择或明确委托，不得把建议直接写成决定。

## 建立 Harness

用户确认完整契约后，调用项目注册入口。需要多个 cron 时重复传入 `--cron`：

```bash
<skill-directory>/scripts/perpetuum project add <project-path> \
  --name "<project-name>" \
  --agent <codex-or-claude> \
  --timezone "Asia/Shanghai" \
  --cron "*/5 0-5 * * *"
```

用确认后的内容替换 `goal.md`、`team.md` 和 `history.md`，再通过 Story 接口创建全部初始卡片。`team.md` 不得保留“请确认”等模板占位文字。注册完成时应该至少存在一张 `ready` Story；如果用户明确确认项目当前应当 Idle，可以没有 `ready` Story，但必须在最终摘要中说明。

复核 Story 列表只返回元数据，逐张抽查正文和 front matter；复核 `team.md` 中 Executor 已启用、可选角色的启用策略和调用图无歧义；复核 `schedule.yaml` 与用户确认的时区和 cron 一致。随后启动服务并展示前端地址。若配置地址已经运行同一运行时目录的 Perpetuum 前端，直接复用，不重启，也不另选端口：

```bash
<skill-directory>/scripts/perpetuum start
```

若端口被其他服务或不同运行时目录的 Perpetuum 占用，停止并向用户说明冲突；不要擅自结束该服务、重启它或自动换端口。

注册结果只在 `project.yaml` 中记录 Agent 类型，在 `team.md` 中记录业务角色编排，在 `schedule.yaml` 中记录时区和 cron。不要把 shell alias、可执行文件绝对路径、权限参数或 cc-use 运行参数写入项目配置；这些由 Runner 和 cc-use 各自统一管理。

## 确认门槛

“用户说了一个长期方向”“用户回答了某一轮问题”或“Agent 已经给出建议”都不等于授权建立 Harness。最终契约中不能出现“待定”“沿用默认”“之后再说”或未被明确委托的 Agent 推断。

用户尚未确认时，把草稿和待决清单保留在当前对话中，不写入 `~/.perpetuum/projects/`。只有运行环境的纯事实可以通过检查得到；所有长期行为和授权仍需用户明确。

## Goal 的要求

`goal.md` 不是一句口号。根据项目需要写清长期目标、当前背景、可用资源、禁止触碰的边界、成本和安全底线、长期有效的特殊要求，以及什么证据能够说明真实进展。

Goal 不保存 Story 列表。具体业务工作统一保存在 `stories/*.md`；执行过程中的步骤不进入全局 Story 模型。
